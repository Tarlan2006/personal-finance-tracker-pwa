# Аудит совместимости Safari — 03.11.2026

## Среда и границы

Windows, Playwright WebKit 27.2 (build 2370), мобильные viewport 393×852 и 402×874, DPR 3, светлая/тёмная тема. Дополнительно Chromium с touch/CDP и такими же размерами. Это проверка двух движков, не физического iPhone и не конкретной установленной версии Safari. По [документации Playwright](https://playwright.dev/docs/browsers#webkit), тестовый WebKit не является брендированным Safari; наиболее близкая среда требует macOS. Ограничения защитного режима подтверждены [документацией WebKit](https://webkit.org/blog/13966/webkit-features-in-safari-16-4/#new-restrictions-in-lockdown-mode), но искусственный запрет API не воспроизводит все ограничения iOS.

Реальные выписки используются только локально для сверки. Финансовые сценарии выполняются в локальной SQLite/D1 на вымышленных аккаунтах и публично безопасных фикстурах. Публичная проверка — без входа и изменения финансовых данных.

## Найдено и исправлено

| Риск | Исправление и проверка |
|---|---|
| До завершения стартовых запросов React возвращал пустой экран; сетевая ошибка маскировалась экраном входа | Видимый стартовый статус, через 12 секунд — сообщение о длительной загрузке и ручной повтор. Ошибка API отображается явно; 401 по-прежнему ведёт на вход. Таймер не опрашивает сервер. |
| При недоступном JS-бандле HTML содержал пустой root | Статическое сообщение и ссылка повторного открытия доступны до запуска JavaScript; отдельный тест прерывает загрузку бандла и восстанавливает её. |
| Safari может запретить само свойство navigator.serviceWorker или синхронно отклонить регистрацию | Изолированная необязательная регистрация с обработкой синхронных и асинхронных отказов; updateViaCache:none. Тесты охватывают отсутствующий API, getter, sync/async ошибку и штатный вызов. |
| После ошибки облачного файла повторный выбор того же файла мог не дать change | Значение file input сбрасывается после получения File. Выбранный File остаётся в памяти чтения; повторный выбор проходит обработку заново. Проверены NotReadableError и последующий dryRun того же PDF. |
| IndexedDB.open мог зависнуть навсегда, удерживая вход/сохранение | Открытие ограничено 5 секундами; blocked и abort явно отклоняются. Позднее соединение закрывается без транзакции/записи. Очередь не удаляется, интерфейс не обещает успешное сохранение при отказе. |
| Прежние тесты прокрутки/Service Worker зависели от Chromium API | Полные проекты WebKit добавлены отдельно. SW проверяется через инструментированный скрипт в настоящем браузере; без context.serviceWorkers() и CDP. |

Ранее исправленное отсутствие Cache Storage сохранено и проверено при install/activate, сетевом чтении, offline и обновлении. Успешная сеть не зависит от кэша, API не кэшируются; при недоступности сети и кэша возвращается страница повтора (503), HTML не подставляется вместо JS/CSS.

## Сценарии

Запуск без сессии, вход/ошибка пароля, восстановление сессии, загрузка JS и API с отказами/зависанием, отсутствие localStorage, зависший/запрещённый IndexedDB, недоступность регистрации SW. Для Cache Storage: отсутствующее свойство, бросающий getter, отказ методов, онлайн/офлайн/восстановление; отдельно проверена замена сломанного старого SW без очистки пользовательского хранилища.

Прокрутка: анкета с семью счетами, длинные списки, собственная область шторки, восстановление документа после закрытия, повторные открытия, фокус полей, viewport 320×568, 393×430 и 852×393, отсутствие горизонтального переполнения. Chromium проверяет настоящие браузерные touch-события CDP. Mobile WebKit Playwright не поддерживает wheel/CDP swipe: там проверяются DOM-прокрутка, геометрия, focus, lock/unlock и восстановление; физический жест iOS не заявляется проверенным. Изменение viewport — проверка раскладки, не системной клавиатуры.

PDF: вымышленные Kaspi Gold/депозит/русский, Halyk и Freedom; скачать → выбрать файл → dryRun → импорт → отчёт → получатели; повтор без новых операций; 2 МиБ и повреждённый файл; смена банка при незавершённом чтении; чтение файла из облака с отказом; все строки/служебные строки/отклонения и история. Для каждого из трёх банков имитируется потеря HTTP-ответа после успешной записи: повтор даёт только duplicate, число финансовых записей не растёт сверх исходного импорта. Сумма четырёх статусов равна total.

## Повторяемые команды

```powershell
npx.cmd playwright install webkit
npm.cmd run typecheck
npm.cmd test
npm.cmd run build
npm.cmd run test:safari
$env:CHROMIUM_PATH='C:/Program Files/Google/Chrome/Application/chrome.exe'
npm.cmd run test:e2e
npm.cmd run test:import-runtime
npm.cmd run scan-secrets
npm.cmd run verify:safari -- https://qarjy.tarlan-b06.workers.dev
```

Два проекта одного движка запускаются отдельными командами через npm-скрипт: локальная база пересоздаётся, проверка смены пароля не переносит состояние между проектами. Сборку нельзя запускать параллельно браузерному прогону. Публичный verify:safari проверяет вымышленные PDF по SHA-256, две темы, закрытый API истории, три варианта отказа кэша и обновление SW. Подмена ответа sw.js происходит только в отдельном тестовом браузерном контексте, сервер не меняется.

## Непроверенное

Физический iPhone, точная версия Safari владельца, системный режим блокировки, файлы из iCloud/приложения «Файлы» через настоящий picker, реальная клавиатура/VisualViewport, rubber-band/momentum и системные жесты, VoiceOver, установка и обновление PWA с домашнего экрана, выгрузка вкладки ОС под давлением памяти. Поэтому аудит устраняет найденные дефекты и закрепляет регрессии, но не гарантирует отсутствие всех будущих ошибок Safari. Боевые нагрузочные лимиты Cloudflare и авторизованная запись в клиентскую D1 не проверяются этим аудитом.
