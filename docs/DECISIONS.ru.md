# Решения (DECISIONS.md)

Все решения приняты без вопросов к владельцу, по заданию «основа проекта». Если что-то не подходит — меняется отдельным заданием.

## Проект
1. **Название.** Рабочее: **Қаржы** («финансы» по-казахски), каталог и Worker — `qarjy`. Заменяется поиском/заменой (`qarjy`, `Қаржы`). Варианты на выбор: *Tenge*, *Aqsha* («деньги»), *Jamyr*. Владелец просил помочь с названием; окончательно решает он.
2. **Каталог `reference/finance-tracker/`.** Папка проекта была пустой, референса нет. Основа написана с нуля по описанию в задании. Практики перенесены по описанию (идемпотентность, очередь, хеши паролей, сессии, отзыв устройств, блокировки, заголовки, `no-store`, SW только для оболочки). `reference/` добавлен в `.gitignore`. **Список категорий по умолчанию не сверялся со старым проектом** (его не было) — составлен заново, см. ниже.
3. **Предметная область.** Задание описывало нейтральную основу; в пожелании владельца описан домен «выписки Kaspi/Halyk/Freedom + ручной ввод + категории + графики». Реализован **домен денег** как отдельный слой (`worker/src/domain/money/`, миграция `0002_money.sql`), ядро (`0001_core.sql`, auth, ключи, очередь) осталось нейтральным. Банковские парсеры **не написаны**: образцов выписок нет, а форматы (PDF/XLSX/CSV, колонки, статусы) нельзя угадывать — иначе строки будут теряться или искажаться.

## Хранилище и сервер
4. **D1 вместо Google Sheets** (как в задании). Интерфейс `Store` — тонкая обёртка над D1 со счётчиком обращений; второй реализации (Sheets) нет, и не требовалось.
5. **Без Durable Objects.** Сериализацию записей на аккаунт заменяют: (а) `PRIMARY KEY (account_id, id)` + `ON CONFLICT DO NOTHING` — идемпотентность на уровне базы; (б) `D1.batch()` — одна транзакция на запись+контрагента; (в) оптимистичная блокировка по `version` для правок (`UPDATE … WHERE version = ?` → 409); (г) уникальный индекс `(account_id, dedupe_key)` для импорта. Это проще и дешевле по лимитам, чем DO, и не требует сериализации, поскольку все конфликты решаются условиями SQL. DO понадобится, если появятся записи с чтением-изменением-записью без версии.
6. **Деньги — целые тиыны** (`value` со знаком + `amountMinor` в JSON). Никаких float.
7. **Время.** Хранится UTC-миллисекундами; месяцы и «день без времени» считаются по UTC+5 (Казахстан, единый пояс). Дата без времени = 12:00 местного, чтобы не прыгать через сутки.
8. **Категория записи вычисляется при чтении**: явная категория записи → привязка получателя (отдельно для расхода и дохода) → правило по подстроке → «без категории». Поэтому смена привязки сразу перекатегоризирует всю историю, а удаление категории (мягкое) не ломает записи. Цена: на чтение уходит один `batch` из трёх SELECT (категории, привязки, правила).
9. **Классификация доходов/расходов** — детерминированная, без ИИ: направление берётся из выписки (знак, колонки списания/зачисления или колонка типа). Категории доходов («Зарплата» и др.) — привязкой получателя или правилом по тексту; стартовые правила: «зарплат», «заработн», «salary» → Зарплата.
10. **Категории по умолчанию** (составлены заново): расходы — Магазины, Кафе и рестораны, Транспорт, Связь и интернет, Здоровье, Развлечения, Другое; доходы — Зарплата, Переводы, Подарки, Возврат долга, Другие доходы. Пользователь может менять, добавлять, удалять.
11. **Импорт: «ни одна строка не пропадает».** Каждая строка файла получает статус `imported` / `duplicate` / `rejected` (с причиной и номером строки), инвариант `imported + duplicates + rejected = total` проверяется в коде и тестами. Одинаковые строки внутри одного файла считаются разными операциями (в ключ входит порядковый номер среди идентичных), повторная загрузка того же файла даёт 0 новых. Ограничение: если пересекающиеся выписки отличаются порядком идентичных строк, возможны ложные дубли/пропуск — банковский профиль должен использовать уникальный номер операции, когда он есть. Откат импорта целиком возможен (`DELETE /api/import/batches/:id`).
12. **Удалённая вручную запись, пришедшая из импорта, при повторном импорте считается «дублем»** (чтобы удалённое не воскресало). Для полного пересоздания — откат пакета.

## Безопасность
13. **Пароли:** PBKDF2-SHA256, 100 000 итераций (потолок Workers), соль на аккаунт; сравнение за постоянное время; при неверном логине выполняется фиктивное хеширование.
14. **Сессии:** случайный токен, в БД — SHA-256, cookie `HttpOnly; Secure; SameSite=Strict`, 30 дней; отзыв по устройству; смена пароля отзывает остальные устройства. `last_seen` пишется не чаще раза в час (экономия записей).
15. **Блокировка:** 5 неверных паролей → 15 минут (`429` + `Retry-After`); плюс 30 попыток входа / 10 мин на IP.
16. **Выход только онлайн.** cookie `HttpOnly` очистить может только сервер; офлайн-«выход» оставил бы живую сессию. Поэтому без сети выход отклоняется с понятным сообщением.
17. **Ключи API:** `qk_w_…` / `qk_r_…`, 30 байт случайности, в БД SHA-256, показываются один раз, отзыв одной кнопкой, `last_used_at` (не чаще раза в минуту), 60 запросов/мин, тело ≤ 4 КБ, максимум 20 активных. Ключ не принимается на маршрутах приложения, cookie не принимается на маршрутах «Команд».
18. **CSRF:** SameSite=Strict + проверка `Origin` на изменяющих запросах + обязательный JSON `Content-Type`.
19. **Заголовки:** CSP (`default-src 'self'`), `nosniff`, `X-Frame-Options: DENY`, HSTS, `Referrer-Policy: no-referrer`, `no-store` для всего `/api`.
20. **Экспорт CSV** экранирует ячейки, начинающиеся с `= + - @` (защита от CSV-инъекции).
21. **Список аккаунтов на экране входа публичный** (`GET /api/accounts`) — этого требует выпадающий список из задания. Отдаются только логин и отображаемое имя активных аккаунтов. Если аккаунтов станет много или имена станут чувствительными, надо перейти на ввод логина.
22. **Очередь офлайн шифруется при выходе** AES-GCM, ключ — случайные 32 байта аккаунта на сервере (отдаются только после входа). Это защищает данные очереди на устройстве после выхода; пока пользователь вошёл, очередь лежит в IndexedDB открыто (так и в браузере устройства нет защищённого хранилища).

## Клиент
23. **React 18 + Vite + TypeScript**, графики — собственный SVG (без библиотек). JS 58.6 КБ gzip (лимит ~100).
24. **Правки и удаления офлайн не ставятся в очередь** — только добавление. Причина: для правки нужен контроль версий/конфликтов; в этом задании не делалось.
25. **Опрос:** клиент не опрашивает сервер по таймеру. Данные грузятся при открытии экрана и после собственных изменений. Очередь повторяет отправку только после сбоя (backoff 5 с → 15 мин + jitter, `Retry-After` приоритетнее) или при `online`/возврате в приложение. Одинаковые одновременные GET объединяются.
26. **Service worker** кеширует только оболочку (`/`, `/assets/*`, manifest, иконки); `/api/*` не кешируется никогда; регистрируется только на https.
27. **Тесты в среде без `wrangler`/`workerd`.** Серверная логика тестируется на настоящем SQLite (`node:sqlite`) через адаптер D1 (`worker/dev/sqlite-d1.ts`) с теми же файлами миграций. Различия D1 и SQLite этого адаптера (лимиты, `meta`) могут проявиться только в боевой среде — поэтому в README есть шаги проверки после деплоя.
28. **WebKit недоступен в среде** → браузерные тесты идут в Chromium с эмуляцией iPhone (размеры, DPR, touch, UA). Это не Safari.

## Не делалось в исходной версии (историческая запись)
Web Push (только архитектурное место: таблицы можно добавить миграцией `0003`, подписка привязывается к `sessions.id`); выгрузка в Google Sheets (интерфейса-экспортёра в коде нет — только CSV); офлайн-правки; профили Kaspi/Halyk/Freedom; несколько валют (везде KZT).


## Профили банков

Проверены локально четыре PDF-образца; реальные данные не сохранены в исходниках, фикстурах или документации. CSV/XLSX среди образцов нет, поэтому банковские CSV/XLSX-профили не добавлены. Универсальный CSV сохранён. Выбор банка явный: похожие таблицы без надёжной сигнатуры не определяем автоматически.

- **Kaspi, депозит:** текстовый PDF A4, казахская шапка «Күні / Сомасы / Операция / Толық ақпарат / Депозитте». Сверху реквизиты и сводка, ниже операции; шапка повторяется на следующей странице. Дата dd.MM.yy, сумма со знаком, пробелами группировки и десятичной запятой, символ ₸. Последний столбец — остаток, не сумма операции. Поддержан.
- **Kaspi Gold:** PDF с сопроводительной страницей и таблицей «Күні / Сомасы / Операция / Толығырақ». Даты и суммы аналогичны депозиту; встречаются переносы типа операции. Поддержан. Получатель — отдельная колонка деталей, исходные тип и детали сохраняются в note. Продолжения деталей добавляются к получателю и note.
- **Halyk:** текстовый PDF A4 с английскими заголовками: даты операции и обработки, описание, сумма и валюта операции, Credit in account currency, Debit in account currency, Fee, номер карты/счёта. Дата dd.MM.yyyy, запятая и неразрывные пробелы в суммах. Берём первую дату, направление и сумму из отдельных колонок зачисления/списания. Остатки и сводки не импортируем. Поддержаны операции KZT; иная валюта явно отклоняется. Описание бывает многострочным и содержит технические ключи локализации: сохраняем его как есть, не пытаемся угадать имя за ключом. Комиссия отдельно не создаётся.
- **Freedom:** текстовый PDF Letter, первая страница с реквизитами и сводкой, далее «Дата / Сумма / Валюта / Операция / Детали». dd.MM.yyyy, десятичная точка и запятая группировки. **ready: true**. Строки связываются по векторным границам ячеек, а не ближайшей дате: многострочный текст центрирован по высоте. Поддержаны страницы продолжения без повторной шапки после проверки предыдущей таблицы. Последний фрагмент описания без даты связывается только с первой операцией следующей страницы; неоднозначный или оборванный фрагмент отклоняет файл до записи. Направление — знак суммы; только KZT, блокировки/ожидание и явно указанные собственные переводы отклоняются. Получатель выделяется по «Отправитель:», «Получатель:», суффиксу «Мгновенный перевод» либо префиксу перед «По договору №»; неизвестный текст остаётся исходным. Если он длиннее 120 символов, получатель пустой, полное описание сохранено в note.

Серверная зависимость unpdf (PDF.js для serverless) не входит в клиентскую сборку. PDF передаётся base64; ограничения 2 МиБ, 100 страниц, предел атомарного импорта 1000 строк. Внешние ресурсы не запрашиваются. Повреждённый PDF возвращает общую ошибку без текста документа в журнале. Геометрия колонок ограничена изученными макетами A4 (Kaspi/Halyk) и Letter (Freedom); другие версии выписок не заявлены поддержанными. Работа PDF.js в настоящем Worker и его CPU/память ещё не проверены.

Учёт строк PDF: total — число непустых извлечённых текстовых строк **под шапками таблиц**, а не число страниц или банковских операций. Шапки, обложки и реквизиты над таблицей не являются строками операций. Продолжения описаний и служебные строки под таблицей получают rejected с причиной; текст продолжения одновременно сохранён в операции. Поэтому rejected сам по себе не означает потерянную операцию. Номер строки отчёта относится к промежуточной таблице, не к координате в PDF. Для всех строк отчёт содержит статус, включая imported.

Направление — только знак (Kaspi/Freedom) либо дебет/кредит (Halyk), без ИИ. Отдельной колонки статуса в поддержанных образцах нет; распознаваемые явные типы «Отклонена», «Не завершена», «Ожидает», «Сумма в блокировке» отвергаются. Прочие варианты статусов и языков не заявлены проверенными. Свои переводы не выводим из совпадения имён или номеров: только явный тип «перевод между своими счетами» даёт такую причину отклонения, остальные импортируются обычными операциями. Это может включать собственные пополнения депозитов.

У поддержанных таблиц нет подтверждённого уникального **номера операции**. Номер карты, договора, счёта и документа-сопровождения не подходят. Сохраняется схема account_id + bank + дата/направление/сумма/нормализованные получатель и note + порядковый номер одинаковой операции. Повтор файла даёт ноль новых; пересекающиеся периоды без неразличимых операций дедуплицируются. Ограничение: различное количество одинаковых операций или изменение описания между выписками может дать ложный дубль либо новый импорт. Между Gold и депозитом нет идентификатора исходного счёта, поэтому одинаковые операции этих счетов также могут совпасть. Гарантия идеальной дедупликации пересечений отсутствует. normName используется в ключах, исходный текст остаётся в note.

Синтетические PDF в worker/test/fixtures созданы с нуля, без копирования объектов, метаданных, страниц и значений из образцов. Тесты проверяют суммы в тиынах, даты UTC+5, направления, получателей, переносы, отклонение незавершённой операции, полный отчёт, повтор, dryRun, размер и изоляцию аккаунтов. Счётчик X-Storage-Ops сохранён, бюджет 500 строк — максимум 20 вызовов (batch считается одним обращением, не одной SQL-командой).


### Уточнения после аудита импорта

Аудит и оставшиеся препятствия описаны в IMPORT_AUDIT.ru.md. Непустая нераспознанная колонка дебета/кредита теперь отклоняет всю строку. Импорт не обрезает имя длиннее 120 или note длиннее 300 символов: строка получает rejected для ручной проверки, чтобы не менять получателя и ключ дубля молча. Прикладные ограничения ручного ввода не менялись. JSON null/массив вместо параметров импорта возвращает 400.

Эталоны выбора колонок — worker/test/fixtures/examples.json, используемый Vitest. Это детерминированные правила и тестовые данные, не обучение ИИ. Проверка реальных исходников выполняется только локально scripts/audit-bank-samples.ts; лог содержит счётчики и булев результат, исходные значения не сохраняются.


### Атомарность и лимиты импорта (после аудита)

Два блокирующих риска аудита закрыты. Выбран ограниченный синхронный импорт вместо долгого фонового задания: **не больше 500 строк за запрос**, включая отклонённые строки и продолжения PDF. Для больших выписок пользователь делит файл по непересекающимся датам, не разрывая операции одного дня: это не сбрасывает порядковый номер одинаковых операций между частями. Если за один день больше лимита, текущий синхронный импорт такого дня не поддержан; нельзя обходить лимит произвольными фрагментами с одинаковыми операциями. Прежний предел 20 000 отменён. CSV без шапки также допускает ровно 500 строк; PDF прекращает подготовку при превышении лимита, до финансовых записей. Размер файла остаётся прежним; дополнительный предел — 20 000 текстовых элементов на страницу PDF.

Операции, новые контрагенты, полный отчёт import_batches и чтение этого отчёта теперь выполняются в **одном D1.batch**. Любая SQL-ошибка откатывает всю последовательность. Никаких промежуточных коммитов по 40 операций больше нет. Изменений схемы и миграций не требуется.

Статусы imported/duplicate вычисляются SQL в той же транзакции после вставок: проверяются candidate entry.id, account_id и import_id. Это не предварительный SELECT: при одновременных загрузках уникальный ключ выбирает победителя, а проигравший пакет сохраняет точные duplicate-статусы. Внутренние candidate ID удаляются из JSON отчёта. Откат пакета, account isolation и старые ключи дедупликации сохранены.

Чтение категорий/привязок, хеширование и проверка размера отчёта происходят до записи. После COMMIT нет дополнительных обращений к БД для подготовки ответа. Если ответ потерян после успешного COMMIT, записи **и отчёт** уже сохранены; ошибка не утверждает, что данных нет. Повтор файла безопасен: существующие операции становятся дублями. Если транзакция не закоммичена, не остаётся ни операций, ни контрагентов, ни отчёта. Отсутствующие отчёты от старой версии автоматически не восстанавливаются.

JSON отчёта проверяется до транзакции: максимум 1 000 000 байт с запасом 1024 байта; причины ограничены 200 символами, preview — прежними 140. Исходный JSON содержит ещё и служебные candidate ID; сохраняемый JSON удаляет их и укорачивает причины успешных строк, поэтому не превышает проверенную оценку. Запас по сравнению с 2 000 000 байт D1 оставлен и для остальных колонок. При превышении — 413 и ноль финансовых записей. Число параметров отдельного SQL не превышает 100, текст каждого SQL короче 100 КБ.

Счётчик X-Storage-Ops считает batch одним вызовом согласно документации D1. На 500 строк измерено: непосредственно импорт 2 вызова (метаданные + атомарная транзакция), dryRun — 7; через HTTP с авторизацией и ограничением частоты — 4 и 9. ## Стартовая финансовая анкета — 02.11.2026

1. После аутентификации, до ленты, клиент загружает финансовый профиль. Новый аккаунт (включая ранее созданный аккаунт без анкеты) видит пятишаговый опрос. До аутентификации финансовая информация не собирается. Статусы: new (строки в БД нет), draft, deferred, complete. После завершения/откладывания повторный вход сразу открывает ленту. Для draft ответы восстанавливаются, шаг начинается со счетов; номер шага не сохраняется. Продолжение и редактирование доступны через «Ещё».
2. Вопросы: банки (Kaspi/Halyk/Freedom/другой банк), отдельные карты/депозиты/текущие счета/наличные, дата и начальные остатки; важные существующие категории расходов, месячный план и размер домохозяйства; источники дохода, существующая категория и регулярность, сумма в месяц; регулярные платежи и остатки долгов; одна главная цель, её сумма и план накоплений. Все финансовые разделы можно оставить пустыми. Пустая сумма — null, не ноль; отрицательный остаток допускается только для карты/текущего счёта. Валюта KZT, деньги — целые тиыны. Не собираем документы, ИИН, номера карт, CVV и банковские пароли; свободные поля пользователь должен заполнять названиями для себя.
3. Миграция только новая: 0003_financial_profiles.sql. Один ограниченный JSON-снимок на account_id, без записи фиктивных операций. GET/PUT /api/financial-profile принимают только сессию, account_id берётся из сессии. Изоляция и чужие категории проверены серверными тестами. Строки ограничены по длине, до 30 счетов/доходов/обязательств, 100 категорий, до 24 000 байт сохранённого JSON и 32 КиБ тела запроса. Каждое сохранение — одна SQL-запись с проверкой версии; конфликт 409 не перезаписывает чужую вкладку. Обход account_id через тело невозможен.
4. Сохранение только по явному нажатию, без опроса таймером, без записи анкеты в localStorage/IndexedDB. «Сохранить и продолжить» сохраняет весь валидный черновик; ошибка сети оставляет экран и введённые ответы до перезагрузки. Перезагрузка восстанавливает последнее успешное сохранение, несохранённые изменения не гарантируются. При конфликте предлагается обновить страницу, автоматического слияния нет. GET = 2 обращения с проверкой сессии, PUT = 3; бюджеты X-Storage-Ops в ops.test.ts. Данные сессии и анкеты сбрасываются при выходе; все /api ответы no-store.
5. Категории из анкеты становятся первыми в форме добавления, но остальные доступны и история не переклассифицируется. Источники доходов и цели не создают автоматических правил. Удалённые категории не мешают редактированию: отсутствующие предпочтения убираются, источник остаётся без категории. Первый поддержанный банк из счетов становится выбором по умолчанию в PDF-импорте; явный выбор сохранён.
6. Остатки — снимок на выбранную дату, а не текущий баланс. Нет привязки существующих операций к конкретному счёту, сверки остатков с выпиской, учёта внутренних переводов, нескольких валют, автоматического планирования платежей или прогресса целей. Не вычитаем долги из суммы остатков молча. Анкета не меняет импорт, дедупликацию, месячные фактические отчёты и финансовые записи.

Локальный SQLite-адаптер теперь ведёт local_schema_migrations и применяет новые миграции транзакционно при повторном запуске. Для старых баз фиксирует уже существующие 0001/0002 по наличию их таблиц, затем добавляет 0003; отдельный тест проверяет сохранение аккаунта/категорий и повторный запуск. Это относится только к dev/test. На Cloudflare миграция по-прежнему применяется отдельной командой владельца перед деплоем.

## Отдельный учёт служебных строк — 02.11.2026

По запросу владельца прежний инвариант из трёх статусов заменён: `imported + duplicates + rejected + service = total`, число элементов rows равно total. `service` — пустая строка, банковский служебный текст или продолжение описания; это не отклонённая операция. Каждый такой элемент сохраняет номер и причину, новые банковские отчёты также полный текст. Продолжения по-прежнему добавляются к исходному описанию операции. Шапка и логические строки извлекаются по прежним правилам PDF; total не означает число визуальных строк всего документа.

«Отклонено» содержит только неподдержанную/некорректную операцию с причиной (в том числе ожидание, валюта, надёжно определённый собственный перевод). Строка с финансовыми признаками и неверной датой/суммой не переводится в service. Итоговая валютная строка Halyk распознаётся отдельно. Пользовательский универсальный CSV не может объявить строку служебной через внутреннюю колонку банковского парсера; пустые CSV-строки учитываются как service.

Интерфейс показывает пять счётчиков и отдельные разделы отклонений, повторов и служебного текста. Служебный раздел свёрнут; строки раскрываются порциями по 100, доступны все строки. «История импортов» загружает последние 50 пакетов по запросу и позволяет открыть сохранённый отчёт без повторного импорта. Каждый запрос ограничен account_id.

Новая миграция 0004 добавляет import_batches.service и переклассифицирует только полные сохранённые отчёты с точной прежней причиной банковского служебного текста либо подтверждённой пустой строкой. Порядок, номера и текст не удаляются; imported/duplicates, entries и dedupe_key не меняются. Неполные старые отчёты не переинтерпретируются. Полный текст, ранее обрезанный в preview, восстановить миграцией невозможно. Чтение дополнительно нормализует полный старый отчёт, если прежний Worker завершил запись во время обновления. Схема совместима с прежними INSERT благодаря DEFAULT 0; миграция применяется перед новым Worker.

Атомарная D1.batch сохранена, дополнительные обращения при записи не добавлены. Ограничения размеров и JSON-параметра, бюджет на 500/1000 строк и откат при ошибке остаются обязательными. Дедупликация не меняется: локально на восьми исходных PDF подтверждено точное совпадение всех ключей принимаемых операций с прежним парсером. Ограничения пересекающихся периодов без банковского ID остаются прежними. Реальные данные используются только локально, синтетические тесты и публичные примеры не содержат оригиналов.

## Недоступный Cache Storage в Safari — 03.11.2026

По скриншоту владельца загрузка прерывалась внутри Service Worker: прямое обращение к отсутствующей глобальной переменной caches вызывало ReferenceError, а обработчик сетевой ошибки повторял это обращение. Cache Storage теперь необязателен: получение self.caches, открытие/чтение/запись и очистка обёрнуты в обработку отказа. Успешный ответ сети возвращается независимо от доступности кэша. Установка и активация завершаются даже при запрете хранилища, новая версия захватывает клиентов через skipWaiting/claim. Версия оболочки v2; удаляются только прежние qarjy-shell-*, чужие кэши не затрагиваются.

Если сеть недоступна, используется собственный кэш оболочки; fallback на HTML разрешён только для навигации, не для JS/CSS. При отсутствии сети и кэша навигация получает HTTP 503 с русским сообщением и кнопкой повтора; ресурс получает сетевую ошибку. API, внешние адреса и не-GET запросы Service Worker не перехватывает. Блокировку/защиту Safari отключать не требуется. Эта правка не гарантирует офлайн-работу в режиме, который запрещает хранилище; данные IndexedDB и финансовая база не очищаются и не изменяются.

Добавлен отдельный регулярный WebKit-прогон npm run test:safari (две мобильные темы); CHROMIUM_PATH действует только на Chromium. Windows WebKit проверяет другой движок, но не заменяет физический Safari iOS. Детальный протокол и ограничения — SAFARI_AUDIT.ru.md. Публичный npm run verify:safari не входит в аккаунт и не создаёт финансовые записи; подмены SW изолированы внутри тестового браузерного контекста.

Запуск имеет видимый статус и статический HTML при недоступном бандле. Через 12 секунд доступен ручной повтор; при сбое API показана причина, только 401 означает экран входа. Сервер не опрашивается таймером. Регистрация SW необязательна, синхронные/асинхронные отказы и запрещённый getter перехватываются, updateViaCache:none.

Открытие IndexedDB ограничено 5 секундами: blocked/timeout/abort — ошибка без обещания сохранения. Позднее соединение закрывается; очередь/база не очищаются. Это не тайм-аут финансовой серверной записи. Для потерянного HTTP-ответа импорта правило прежнее: проверить историю/повторить, атомарная запись и дедупликация исключают новые дубли.

## Подтверждение импорта и удаление истории — 03.11.2026

Перед записью файла открывается шторка «Подтвердить импорт» с именем файла и банком. «Проверить» остаётся dryRun без записи. Итоги проверки в подтверждении показываются только при совпадении текущих настроек колонок с проверенными; смена колонок не выдаёт старый прогноз за новый. Отмена подтверждения не делает POST импорта.

«История импортов» доступна на экране «Выписка» и в «Ещё → История и очистка». Каждая карточка показывает банк/CSV, имя, время, исторические счётчики и число активных операций сейчас. Пагинация по (created_at,id), по 50 пакетов, не теряет загрузки с одинаковым временем. Исходные PDF/CSV сервер не хранит — хранятся извлечённые операции и отчёт.

DELETE /api/import/batches/:id теперь требует JSON {confirmation:"DELETE_DOCUMENT",accountLogin:"логин"} и физически удаляет отчёт и все принадлежащие пакету entries, включая мягко удалённые и отредактированные. Это заменяет прежний мягкий undo: интерфейс прямо предупреждает, что восстановить удаление кнопкой нельзя; исходный файл можно загрузить заново. Операции других пакетов и ручные записи не удаляются. Повтор несуществующего/чужого ID возвращает нулевые счётчики, без раскрытия существования чужого пакета. Совпадающие строки других документов не являются владением этой загрузки: документ-дубль не удаляет оригинальные операции, а при пересечении удаляются только новые строки своего пакета.

Одной D1.batch также очищаются контрагенты, не используемые оставшимися entries (в том числе оставшиеся после переименований). Проверка использует нормализованный префикс search, поэтому неоднозначные совпадения сохраняются консервативно. Используемые в других записях получатели/привязки сохраняются; категории и текстовые правила не изменяются. Это не сквозное удаление совпадающих имён/текстов из других документов. После удаления пакета освобождаются его dedupe_key, файл можно импортировать повторно.

GET /api/history/summary возвращает только счётчики своего аккаунта. POST /api/history/clear с {confirmation:"DELETE_ALL_HISTORY",accountLogin:"логин"} одной D1.batch физически удаляет entries (включая ранее мягко удалённые), import_batches и counterparties своего аккаунта. Аккаунт, сессии, API-ключи, категории, правила и финансовая анкета/счета/начальные остатки сохраняются. В UI дополнительно обязателен ввод «УДАЛИТЬ». Повтор при неизменённой базе безопасен; ошибка транзакции откатывает всю очистку. При потере HTTP-ответа UI предлагает обновить историю/повторить вместо обещания, что удаления не было.

Полная очистка в текущем браузере требует пустую и доступную IndexedDB-очередь без сохранённого зашифрованного пакета, отсутствия активной отправки; на время запроса очередь остановлена и затем запускается снова только в той же сессии. При недоступном хранилище проверка очереди отклоняется, очистка не выполняется. Любое удаление через UI блокируется, пока в этом приложении идёт разбор/импорт, в том числе после перехода между экранами. Другие устройства/вкладки и внешние отправители сервер не останавливает: перед очисткой их нужно синхронизировать, отправки после очистки могут создать записи заново. Это ограничение указано в подтверждении. Оригинальный файл на устройстве пользователя не удаляется.

Миграция 0005 добавляет только индексы для account_id/import_id, диапазона нормализованного search при проверке оставшихся получателей и стабильного курсора истории, данные не переписывает. В обычной активной сессии просмотр страницы/сводки — до 2 HTTP X-Storage-Ops; удаление документа/очистка — бюджет 3 (сама транзакция — 1 обращение). Размер пакета не превращается в сетевой цикл удаления по одной операции. X-Storage-Ops считает обращения, а не тарифицируемые прочитанные/записанные строки D1.


Подтверждения удаления привязаны к accountLogin: он сравнивается с логином текущей сессии в уже выполняемом auth-запросе, без дополнительного обращения к D1. При смене cookie/аккаунта в соседней вкладке сервер отвечает 409, данные не изменяются. Клиент также передаёт accountLogin при импорте; несовпадение отклоняется до записи.

## Отчёты: место при назначении категории — 03.11.2026

Причина скачка: каждое изменение version очищало summary через setS(null), удаляло список из DOM и уменьшало высоту документа. После закрытия шторки браузер ограничивал scrollY по укороченной странице; последующий ответ возвращал список уже в начале.

При обновлении того же месяца сохраняется предыдущий отчёт до ответа сервера. Перед заменой данных запоминается первый видимый получатель и его координата в окне; useLayoutEffect компенсирует изменение высоты блоков над списком. Снимок делается перед применением ответа, поэтому прокрутка пользователя во время ожидания не отменяется. Данные другого месяца по-прежнему скрываются, устаревшие ответы отбрасываются. Ошибка обновления оставляет список доступным с сообщением об ошибке, новый запрос по таймеру не запускается.

Если к моменту ответа открыта следующая шторка, компенсация меняет сохранённую позицию body-lock и top, а последний unlock восстанавливает уже скорректированную позицию. При обычном обновлении корректируется прокрутка документа. Native overflow-anchor отключён только в контейнере отчёта, чтобы браузер и приложение не применяли двойную компенсацию. Ключи строк стабильны; перед открытием выбора категории строка получает focus({preventScroll:true}), что позволяет вернуть фокус на неё и в Safari. Выбор категории защищён от повторной отправки, во время сохранения есть статус и отключены варианты.

Сервер, схема, правила классификации и число API-запросов не меняются: PUT привязки и событийное обновление summary остаются прежними. Изменение проверяется по координате получателя в окне, а не равенству scrollY (высота графика/списка категорий может измениться).
