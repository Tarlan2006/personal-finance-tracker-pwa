# Решения (DECISIONS.md)

Все решения приняты без вопросов к владельцу, по заданию «основа проекта». Если что-то не подходит — меняется отдельным заданием.

## Проект
1. **Название.** Рабочее: **Қаржы** («финансы» по-казахски), каталог и Worker — `qarjy`. Заменяется поиском/заменой (`qarjy`, `Қаржы`). Варианты на выбор: *Tenge*, *Aqsha* («деньги»), *Jamyr*. Владелец просил помочь с названием; окончательно решает он.
2. **Каталог `reference/finance-tracker/`.** Папка проекта была пустой, референса нет. Основа написана с нуля по описанию в задании. Практики перенесены по описанию (идемпотентность, очередь, хеши паролей, сессии, отзыв устройств, блокировки, заголовки, `no-store`, SW только для оболочки). `reference/` добавлен в `.gitignore`. **Список категорий по умолчанию не сверялся со старым проектом** (его не было) — составлен заново, см. ниже.
3. **Предметная область.** Задание описывало нейтральную основу; в пожелании владельца описан домен «выписки Kaspi/Halyk/Freedom + ручной ввод + категории + графики». Реализован **домен денег** как отдельный слой (`worker/src/domain/money/`, миграция `0002_money.sql`), ядро (`0001_core.sql`, auth, ключи, очередь) осталось нейтральным. Банковские парсеры **не написаны**: образцов выписок нет, а форматы (PDF/XLSX/CSV, колонки, статусы) нельзя угадывать — иначе строки будут теряться или искажаться.

## Хранилище и сервер
4. **D1 вместо Google Sheets** (как в задании). Интерфейс `Store` — тонкая обёртка над D1 со счётчиком обращений; второй реализации (Sheets) нет, и не требовалось.
5. **Без Durable Objects.** Сериализацию записей на аккаунт заменяют: (а) `PRIMARY KEY (account_id, id)` + `ON CONFLICT DO NOTHING` — идемпотентность на уровне базы; (б) `D1.batch()` — одна транзакция на запись+контрагента; (в) оптимистичная блокировка по `version` для правок (`UPDATE … WHERE version = ?` → 409); (г) уникальный индекс `(account_id, dedupe_key)` для импорта. Это проще и дешевле по лимитам, чем DO, и не требует сериализации, поскольку все конфликты решаются условиями SQL. DO понадобится, если появятся записи с чтением-изменением-записью без версии.
6. **Деньги — целые тиыны** (`value` со знаком + `amountMinor` в JSON). Никаких float.
7. **Время.** Хранится UTC-миллисекундами; месяцы и «день без времени» считаются по UTC+5 (Казахстан, единый пояс). Дата без времени = 12:00 местного, чтобы не прыгать через сутки.
8. **Категория записи вычисляется при чтении**: явная категория записи → привязка получателя (отдельно для расхода и дохода) → правило по подстроке → «без категории». Поэтому смена привязки сразу перекатегоризирует всю историю, а удаление категории (мягкое) не ломает записи. Цена: на чтение уходит один `batch` из трёх SELECT (категории, привязки, правила).
9. **Классификация доходов/расходов** — детерминированная, без ИИ: направление берётся из выписки (знак, колонки списания/зачисления или колонка типа). Категории доходов («Зарплата» и др.) — привязкой получателя или правилом по тексту; стартовые правила: «зарплат», «заработн», «salary» → Зарплата.
10. **Категории по умолчанию** (составлены заново): расходы — Магазины, Кафе и рестораны, Транспорт, Связь и интернет, Здоровье, Развлечения, Другое; доходы — Зарплата, Переводы, Подарки, Возврат долга, Другие доходы. Пользователь может менять, добавлять, удалять.
11. **Импорт: «ни одна строка не пропадает».** Каждая строка файла получает статус `imported` / `duplicate` / `rejected` (с причиной и номером строки), инвариант `imported + duplicates + rejected = total` проверяется в коде и тестами. Одинаковые строки внутри одного файла считаются разными операциями (в ключ входит порядковый номер среди идентичных), повторная загрузка того же файла даёт 0 новых. Ограничение: если пересекающиеся выписки отличаются порядком идентичных строк, возможны ложные дубли/пропуск — банковский профиль должен использовать уникальный номер операции, когда он есть. Откат импорта целиком возможен (`DELETE /api/import/batches/:id`).
12. **Удалённая вручную запись, пришедшая из импорта, при повторном импорте считается «дублем»** (чтобы удалённое не воскресало). Для полного пересоздания — откат пакета.

## Безопасность
13. **Пароли:** PBKDF2-SHA256, 100 000 итераций (потолок Workers), соль на аккаунт; сравнение за постоянное время; при неверном логине выполняется фиктивное хеширование.
14. **Сессии:** случайный токен, в БД — SHA-256, cookie `HttpOnly; Secure; SameSite=Strict`, 30 дней; отзыв по устройству; смена пароля отзывает остальные устройства. `last_seen` пишется не чаще раза в час (экономия записей).
15. **Блокировка:** 5 неверных паролей → 15 минут (`429` + `Retry-After`); плюс 30 попыток входа / 10 мин на IP.
16. **Выход только онлайн.** cookie `HttpOnly` очистить может только сервер; офлайн-«выход» оставил бы живую сессию. Поэтому без сети выход отклоняется с понятным сообщением.
17. **Ключи API:** `qk_w_…` / `qk_r_…`, 30 байт случайности, в БД SHA-256, показываются один раз, отзыв одной кнопкой, `last_used_at` (не чаще раза в минуту), 60 запросов/мин, тело ≤ 4 КБ, максимум 20 активных. Ключ не принимается на маршрутах приложения, cookie не принимается на маршрутах «Команд».
18. **CSRF:** SameSite=Strict + проверка `Origin` на изменяющих запросах + обязательный JSON `Content-Type`.
19. **Заголовки:** CSP (`default-src 'self'`), `nosniff`, `X-Frame-Options: DENY`, HSTS, `Referrer-Policy: no-referrer`, `no-store` для всего `/api`.
20. **Экспорт CSV** экранирует ячейки, начинающиеся с `= + - @` (защита от CSV-инъекции).
21. **Список аккаунтов на экране входа публичный** (`GET /api/accounts`) — этого требует выпадающий список из задания. Отдаются только логин и отображаемое имя активных аккаунтов. Если аккаунтов станет много или имена станут чувствительными, надо перейти на ввод логина.
22. **Очередь офлайн шифруется при выходе** AES-GCM, ключ — случайные 32 байта аккаунта на сервере (отдаются только после входа). Это защищает данные очереди на устройстве после выхода; пока пользователь вошёл, очередь лежит в IndexedDB открыто (так и в браузере устройства нет защищённого хранилища).

## Клиент
23. **React 18 + Vite + TypeScript**, графики — собственный SVG (без библиотек). JS 58.6 КБ gzip (лимит ~100).
24. **Правки и удаления офлайн не ставятся в очередь** — только добавление. Причина: для правки нужен контроль версий/конфликтов; в этом задании не делалось.
25. **Опрос:** клиент не опрашивает сервер по таймеру. Данные грузятся при открытии экрана и после собственных изменений. Очередь повторяет отправку только после сбоя (backoff 5 с → 15 мин + jitter, `Retry-After` приоритетнее) или при `online`/возврате в приложение. Одинаковые одновременные GET объединяются.
26. **Service worker** кеширует только оболочку (`/`, `/assets/*`, manifest, иконки); `/api/*` не кешируется никогда; регистрируется только на https.
27. **Тесты в среде без `wrangler`/`workerd`.** Серверная логика тестируется на настоящем SQLite (`node:sqlite`) через адаптер D1 (`worker/dev/sqlite-d1.ts`) с теми же файлами миграций. Различия D1 и SQLite этого адаптера (лимиты, `meta`) могут проявиться только в боевой среде — поэтому в README есть шаги проверки после деплоя.
28. **WebKit недоступен в среде** → браузерные тесты идут в Chromium с эмуляцией iPhone (размеры, DPR, touch, UA). Это не Safari.

## Не делалось (намеренно)
Web Push (только архитектурное место: таблицы можно добавить миграцией `0003`, подписка привязывается к `sessions.id`); выгрузка в Google Sheets (интерфейса-экспортёра в коде нет — только CSV); офлайн-правки; профили Kaspi/Halyk/Freedom; несколько валют (везде KZT).
