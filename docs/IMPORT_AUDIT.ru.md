Нужен Python с pypdf; путь можно задать через AUDIT_PYTHON. Запуск: `npx.cmd tsx scripts/audit-bank-samples.ts`. Не отправлять вывод дочернего Python или сами выписки во внешние сервисы. Реальные записи даже в локальной SQLite при этой сверке не создаются.

## Найдено и исправлено

1. **P1: повреждённый дебет превращался в доход.** При дебете BROKEN и положительном кредите старая логика считала debit=null пустой колонкой и импортировала доход. Теперь любая непустая, но нераспознанная колонка дебета/кредита отклоняет строку; тест проверяет отсутствие созданных записей.
2. **P1: тихая обрезка описания влияла на дедупликацию.** Разные описания с одинаковыми первыми 300 символами имели одинаковый ключ при отдельном импорте файлов. Теперь импорт отклоняет описания длиннее 300 и имена длиннее 120 символов с явной причиной. Значения не обрезаются молча. Это намеренно консервативное ограничение: такую строку нужно проверить вручную, а не считать дублем.
3. **P2: null вместо JSON-объекта давал внутреннюю ошибку.** Параметры импорта теперь валидируются, null и массив возвращают 400.

## Оставшиеся препятствия для боевой эксплуатации

### P1 — частичная запись без отчёта при сбое

`runImport` пишет операции отдельными транзакциями по 40, а import_batches создаёт после всех пачек. Воспроизведено на вымышленных данных: 41 операция, искусственный сбой второй пачки → 40 записей сохранились, отчётов импорта 0. Клиент получает ошибку без полного отчёта, штатного отката через известный batchId нет. Сбой сохранения отчёта после записей даёт тот же риск. Повтор файла обычно дедуплицирует уже записанное, но это не заменяет журнал и восстановление. Нужен устойчивый жизненный цикл пакета с записью до начала, состоянием выполнения и восстановлением/откатом либо атомарная транзакция всего ограниченного импорта. В этом аудите архитектура импорта не переделывалась.

### P1 — предел 20 000 строк не согласован с D1

При 20 000 допустимых строк текущая запись делает 500 batch-вызовов только для операций, dryRun — 223 SELECT только для дублей. Это выше 50 обращений Workers Free. Бюджет на 500 строк зелёный, но **не доказывает поддержку 20 000**. Кроме того, report_json с preview на каждую строку способен превысить 2 000 000 байт одной строки D1, причём его запись идёт последней. Нужны ограничение по плану и размеру отчёта либо разбивка импорта/отчёта на устойчивые задания. План аккаунта не проверен.

По документации Cloudflare batch считается одним обращением; отдельные SQL внутри него имеют собственные лимиты. Это подтверждает корректность нынешнего X-Storage-Ops как счётчика вызовов, но не покрывает лимиты на данные и CPU:
- https://developers.cloudflare.com/d1/platform/limits/
- https://developers.cloudflare.com/workers/platform/limits/

### P2 — неоднозначная дедупликация

Уникальный ID операции не подтверждён. Используется порядковый номер одинаковых операций. Пересечения с разным числом неразличимых операций не гарантируют точный результат. Gold и депозит имеют общий bank=kaspi без идентификатора исходного счёта; одинаковые операции двух счетов могут ошибочно совпасть. Эти случаи нельзя устранить обучением: нужен источник счёта и надёжный идентификатор/правило разрешения неоднозначности.

### P2 — геометрия и статусы покрыты узко

Проверяется формат страницы и ограниченная часть шапки, координаты колонок фиксированы. Сдвинутый макет того же размера не обязательно будет отклонён целиком. Продолжения описания присоединяются к последней найденной операции; на границах страниц и в подвале возможна ошибочная привязка. Отдельные статусы поддержаны только для известных однотипных строк; перенос статуса или иной язык не доказаны тестами. Нужны многостраничные синтетические кейсы с подвалами, сдвигом колонок, переносами типа операции и проверкой полного note. Существующие компактные PDF — полезные базовые примеры, но не полная копия всех вариантов страниц.

## Примеры: что именно брать

Машиночитаемый эталон: `worker/test/fixtures/examples.json`. Он подключён к Vitest, поэтому ожидаемый отчёт проверяется автоматически. PDF созданы с нуля, содержат TEST SHOP и TEST SENDER; реальных реквизитов в них нет.

| Пример | Дата | Сумма и направление | Получатель | Не брать за сумму |
|---|---|---|---|---|
| kaspi/gold.pdf | Күні | знак Сомасы | Толығырақ + продолжение | тип операции |
| kaspi/deposit.pdf | Күні | знак Сомасы | Толық ақпарат + продолжение | Депозитте: остаток |
| halyk/statement.pdf | первая дата Date of transaction | Credit in account currency → доход; Debit in account currency → расход | Transaction description + продолжение, без догадок | Transaction amount, Fee, остаток |

В каждом поддержанном примере вымышленные операции: расход 12345 тиын и доход 67890 тиын. Повтор — 0 новых, 2 дубля. В Kaspi дополнительно отклоняется синтетическая незавершённая операция. Продолжения и служебные текстовые строки также отражаются в rejected, поэтому total отличается от количества операций.

«Тренировка» здесь означает расширение детерминированных эталонов и тестов. Приложение не обучает модель и не отправляет выписки ИИ. Новую структуру нужно сначала подтвердить локальным образцом, затем создать безопасную синтетическую фикстуру, записать ожидаемые поля и только после этого менять профиль.
